# 终端 / 中控 外设与通信协议说明

> 对应工程：本仓库 `终端-send/`（终端）与 `中控-recv/`（中控）
> 整理日期：2026-09-21（2026-10-09 仓库发布时更新了工程路径）　数据来源：两工程的 `TMPLATE.ioc` 与 `Core/Src/` 下 CubeMX 生成代码（逐项核对，非凭印象）

---

## 1. 两块板的关系

两块板是**同一个 PCB 设计的两份配置**，MCU、时钟、LoRa、OLED、调试口、PWM 通道完全一致，差别只在：

| 差异项 | 终端（send） | 中控（recv） |
|--------|-------------|-------------|
| 光敏电阻 GL5528 | PA0 / ADC1_IN0 | **没有** |
| 土壤湿度 YX55769 | PA1 / ADC1_IN1 | **没有** |
| DHT22 温湿度 | PC15 / 单总线 | **没有** |
| ADC1 + DMA | 有（双通道扫描 + DMA 循环搬运） | **整个外设都没开** |
| **USART2（PA2/PA3）** | **9600** —— 接 CO2 传感器 | **115200** —— 接 ESP8266-12E WiFi |
| 角色 | 采集并上报，等 ACK | 常驻接收，回 ACK，上云 |

两块板烧不同的固件，靠 **470.5MHz LoRa** 通信。**USART2 是同一条物理链路、两种完全不同的对端**，波特率不同是这个工程最容易踩的坑。

## 3. 引脚分配

### 3.1 MCU 与时钟

| 项 | 值 |
|----|----|
| 型号 | STM32F103C8T6（LQFP48，Cortex-M3，64KB Flash / 20KB RAM） |
| 晶振 | HSE 外部 8MHz（PD0-OSC_IN / PD1-OSC_OUT） |
| PLL | HSE × 9 = **SYSCLK 72MHz** |
| AHB | HCLK = 72MHz（÷1） |
| APB1 | PCLK1 = 36MHz（÷2）→ **定时器时钟 ×2 = 72MHz** |
| APB2 | PCLK2 = 72MHz（÷1） |
| ADC | PCLK2 ÷ 6 = **12MHz**（F103 的 ADC 上限是 14MHz） |
| Flash 等待周期 | 2（FLASH_LATENCY_2） |
| SysTick | 1ms，优先级 15（最低） |

> APB1 虽然分频到 36MHz，但 **APB1 上的定时器（TIM4）时钟仍是 72MHz** —— 这是 F103 的固有倍频规则，不是配置错误。

### 3.3 中控板（recv）的差异

**删除**：PA0、PA1、PC15 三个引脚未配置，ADC1 与 DMA 整个外设未启用。

**其余引脚（PA2~PA14、PB0~PB15、PC13、PD0/PD1）与终端板逐项相同。**

**唯一参数差异**：`USART2.BaudRate` = **115200**（终端是 9600）。

共 26 个引脚。

> **踩过的坑**：中控的 `.ioc` 是从终端复制来的，USART2 一开始沿用了 CO2 的 9600，而 ESP8266 的 AT 固件默认 115200。波特率对不上 → AT 指令全被当成乱码丢掉 → 现象是「WiFi 模块连不上热点」。
> **在 USART2 上换模块，先确认对方默认波特率。**

## 4. 各条链路详解

### 4.1 SPI1 —— LLCC68 LoRa 射频（两块板都有）

| 项 | 值 |
|----|----|
| 角色 | 主机（Master），全双工 2 线 |
| 数据宽度 | 8 bit |
| 时钟极性 / 相位 | `SPI_POLARITY_LOW` + `SPI_PHASE_1EDGE` = **SPI Mode 0**（CPOL=0, CPHA=0） |
| 位序 | MSB first |
| 分频 | 32 → **2.25 Mbit/s**（PCLK2 72MHz ÷ 32） |
| 片选 | **软件控制**（`SPI_NSS_SOFT`），PA4 手动拉低/拉高 |
| CRC | 关闭 |
| 超时 | 每次 `HAL_SPI_Transmit/Receive` 100ms |

**为什么是 Mode 0**：LLCC68 手册 §8.2 明确写「SPI 接口对应 Motorola 命名法中的 CPOL = 0 和 CPHA = 0」，且「主设备在 SCK 下降沿产生 MOSI，从设备在 SCK 上升沿采样」。与生成的配置一致。

**四条控制线（都不走 SPI，是独立 GPIO）**：

| 线 | 引脚 | 方向 | 含义 |
|----|------|------|------|
| NSS | PA4 | 输出 | 软件片选，**空闲为高**，每次事务拉低→传完拉高 |
| BUSY | PB0 | 输入 | **高 = 芯片忙，不能收命令**。所有 SPI 事务前必须先等它变低 |
| RST | PB1 | 输出 | 硬件复位，**低有效**，复位时序：拉低 10ms → 拉高 → 等 BUSY 变低 |
| DIO1 | PB10 | 中断 | **上升沿**触发，见 §6.1 |

**一次读寄存器事务的完整时序**（`llcc68_hal.c`）：

```
1. 轮询 BUSY 直到变低（超时上限内）
2. NSS 拉低
3. HAL_SPI_Transmit 发命令字节 + 参数
4. HAL_SPI_Receive 读回数据
5. NSS 拉高
```

> **BUSY 是必需的握手线**（手册 §8.3.1「BUSY 控制线」原文：BUSY 低电平才表示芯片准备好接收新命令，
> 为高时主控**必须等它变低**才能发下一条命令）。几条具体行为：
>
> | 场景 | BUSY 行为 |
> |------|----------|
> | **读**命令 | 不经过内部状态机，直接处理，**BUSY 保持低** —— 读完不用等 |
> | **写**命令 | NSS 上升沿之后 **TSW（所有情况下最大 600ns）**内 BUSY 被拉高表示"开始处理"，处理完再变低 |
> | 芯片要处理**内部 IRQ** 时 | BUSY 也会拉高 —— **这种情况下读命令同样要等** |
> | 睡眠 / FS / RX / TX 模式切换 | 分别在退出睡眠、PLL 锁定、接收就绪、PA 启动完成时变低（表 8-2 有各转换的典型值，如 SLEEP→STBY_RC 冷启动 3500µs） |
>
> 所以 `llcc68_hal.c` 里每次事务前都先轮询 BUSY 变低，不是多余的保险 —— 漏掉会让命令直接丢失。
> SPI 时钟上限是 **16MHz**（手册 §8.2），本工程用 2.25MHz，余量充足。

**射频参数**（`llcc68_p2p.h`，两端逐项相同）：

| 参数 | 值 |
|------|-----|
| 频率 | 470.5 MHz（中国频段 470~510MHz） |
| 扩频因子 SF | SF9 |
| 带宽 BW | 125 kHz |
| 编码率 CR | 4/5 |
| 前导码 | 8 符号 |
| 包头 | 显式（Explicit） |
| CRC | 开启 |
| 发射功率 | 22 dBm |
| 空中速率 | 符号周期 Tsym = 512/125000 = 4.096ms |

**空中时间**（用厂商驱动 `llcc68_get_lora_time_on_air_in_ms()` 实算，非估算）：8 字节 124ms / 10 字节 145ms / 3 字节 104ms。

### 4.2 I2C1 —— SSD1306 OLED（两块板都有）

| 项 | 值 |
|----|----|
| 模式 | I2C 主机，**7 位地址** |
| 速率 | 100 kHz（标准模式） |
| 占空比 | `I2C_DUTYCYCLE_2`（Tlow/Thigh = 2） |
| 自身地址 | 0（主机不占地址） |
| 时钟拉伸 | 关闭 |
| 从机地址 | SSD1306 的 8 位写地址 **`0x78`**（7 位是 `0x3C`，左移一位） |
| 每次写超时 | `OLED_I2C_TIMEOUT_MS` = **100ms** |
| 探测超时 | `OLED_PROBE_TIMEOUT_MS` = **5ms** |

**数据格式**：SSD1306 的 I2C 帧是「从机地址 + 控制字节 + 数据」。控制字节区分命令和数据：

| 控制字节 | 含义 | 代码位置 |
|---------|------|---------|
| `0x00` | 后面是**命令**（如设置页地址、对比度） | `OLED_WR_Byte(..., OLED_CMD)` |
| `0x40` | 后面是**显存数据** | `OLED_WR_Data` |

调用统一是 `HAL_I2C_Mem_Write(&hi2c1, 0x78, <控制字节>, I2C_MEMADD_SIZE_8BIT, <数据>, <长度>, 100)` —— 把控制字节当作「内存地址」来传。

**热插拔机制**（因为只有一块屏，可能插在任一块板上，也可能运行途中被拔掉）：

| 机制 | 效果 |
|------|------|
| 所有 I2C 写先看 `s_oled_online` | 屏不在线 → 直接 return，**一个字节都不发**，零耗时 |
| 任何一次写失败（NACK/超时）立刻把 `s_oled_online` 清 0 | 这就是「运行中拔掉」的检测点，不用额外轮询 |
| `OLED_Init()` 可反复调用，进来先探测 `0x78` | 插回来能重新配置 + 清屏 + 补画标签 |

开销：屏一直不插 → 每次刷新一次探测 ≤5ms；刚插上那一次 → `HAL_Delay(200)` 等电源稳定 + 约 40ms I2C。

### 4.3 USART1 —— 调试串口（两块板都有）

| 项 | 值 |
|----|----|
| 引脚 | PA9 (TX) / PA10 (RX) |
| 波特率 | 115200 |
| 帧格式 | 8 数据位 / 1 停止位 / 无校验（8N1） |
| 硬件流控 | 无 |
| 过采样 | 16 |
| 模式 | 收发双向 |
| 对端 | CH340K → USB → PC 上的 PortHelper |

**数据方向**：`printf` 通过 `fputc()` 重定向到这里（实现在 `debug.c`）。接收用**空闲中断变长接收**（`HAL_UARTEx_ReceiveToIdle_IT`，缓冲 128 字节），收到就把内容原样回显给 PC。

> **这是全工程唯一的日志出口**。所有模块的调试信息都往这里打。

### 4.4 USART2 —— 一条链路，两种对端

参数完全相同的部分：8N1、无流控、过采样 16、收发双向、空闲中断变长接收。

| | 终端（send） | 中控（recv） |
|---|---|---|
| 波特率 | **9600** | **115200** |
| 对端 | CO2 传感器 | ESP8266-12E |
| 缓冲 | `co2_buffer[6]` | `ESP_buffer[128]` |
| 驱动 | `bsp/co2/co2.c` | `MQTT/esp.c` |
| 中断分发 | `ISR_callback.c` → `CO2_UART_Callback()` | `ISR_callback.c` → `ESP_UART_Callback()` |

#### 4.4.1 CO2 传感器帧格式（终端）

依据模块规格书 `3271887116JW01-CO2-V2.2数字信号空气质量模块规格书.pdf`：

| 字节 | 内容 | 值 |
|------|------|-----|
| B1 | 模块地址 | 固定 `0x2C` |
| B2 | CO2 浓度**高**字节 | — |
| B3 | CO2 浓度**低**字节 | — |
| B4 | 满量程高 | `0x03` |
| B5 | 满量程低 | `0xFF` |
| B6 | 校验和 | `(B1+B2+B3+B4+B5) & 0xFF` |

- **CO2 值 = B2 × 256 + B3**（帧内是**大端**，和 LoRa 帧的小端相反）
- 规格书示例：`2C 01 90 03 FF BF` → 校验 `BF = 2C+01+90+03+FF`，浓度 `01×256+90 = 400 ppm`
- 模块**主动周期上报**，MCU 侧只监听、不发送请求（`co2.c` 里没有任何 `HAL_UART_Transmit`）

> **串口只能有一个读者**。`CO2_get_data()` 是死等循环（最长 100ms），读完把 `co2_rx_len` 清 0。
> 如果 LoRa 上报层也去调一次，两边抢同一帧、抢输的必然超时，还会误触发蜂鸣器报警。
> 所以 `co2.c` 里维护 `g_co2_value` / `g_co2_valid` 两个全局量供上报层取缓存值，代价是最多差一个采样周期（CO2 1 秒采一次、2.5 秒发一次）。

#### 4.4.2 ESP8266 AT 指令（中控）

| 项 | 值 |
|----|----|
| 协议 | AT 指令集，TCP 明文透传；报文层为 MQTT 3.1.1（`MQTT/mqtt.c`），应用层 `MQTT/mqtt_app.c` |
| SSID / 密码 / 服务器 | 私密值放在 `MQTT/wifi_config.h`（已 gitignore，模板 `wifi_config.example.h`）；服务器宏在 `MQTT/esp.h` |
| 服务器 | `bemfa.com:9501`（巴法云 MQTT 明文透传口） |
| 重试周期 | 整条链路（WiFi + TCP + MQTT + 订阅）失败后每 `MQTT_RETRY_PERIOD_MS` = **15 秒**重试一次 |

**连接流程**（`ESP_Init()`，最坏约 15.5s）：

```
2s 等待模块启动 → 发 "+++" 退出透传（1s 静默）→ "AT" 重试（1.5s）
→ "ATE0" 关回显 → "AT+CWMODE" 设 STA 模式 → "AT+CWJAP" 连热点（最长 10s）
→ 连 TCP 服务器
```

> **`ESP_Init()` 是阻塞的**。云端连不上时，每 15 秒会阻塞主循环一次（`ESP_Init` 最坏约 15.5s，外加 MQTT CONNECT 与五个主题订阅各等 2s，最坏约 27s），期间 LoRa 收到的包标志不会丢（中断已置位），但会漏包、ACK 会迟发、OLED 会卡一下。要彻底消除得把 `esp.c` 的 AT 流程也改成状态机，目前没做。

### 4.5 单总线 —— DHT22 温湿度（仅终端）

| 项 | 值 |
|----|----|
| 引脚 | PC15，**软件模拟时序**（不占用任何硬件外设） |
| 空闲电平 | 高 |
| 通信速率 | 位宽微秒级，靠 `delay_us()` 精确延时 |
| 采样率 | 支持 0.5Hz（2 秒一次） |

**一次读取的时序**（`dht22.c`，宏在 `dht22.h`）：

```
起始信号：MCU 拉低总线 1ms（HAL_Delay(1)，DHT22 手册要求 ≥0.5ms）
        → 拉高 30us → 切成输入模式释放总线
DHT22 响应：先拉低 80us → 再拉高 80us
然后连续 40 位数据：每位 = 50us 低电平 + 高电平（26~28us=0，70us=1）
40 位 = 湿度高8 + 湿度低8 + 温度高8 + 温度低8 + 校验和8
校验：前 4 字节之和的低 8 位 == 第 5 字节
解析：湿度 = (buf0<<8 | buf1) / 10.0 %RH
      温度 = (buf2<<8 | buf3) / 10.0 ℃，buf2 最高位为 1 表示负温度
```

**返回码**（以 `dht22.c` 的实现为准 —— `dht22.h` 的注释曾经把 1 和 3 写反过）：

| 值 | 含义 | 出处 |
|----|------|------|
| `0` | 读取成功 | `dht22.c:97` |
| `1` | **响应超时** —— 起始信号发完没等到从机应答 | `dht22.c:60` |
| `2` | **数据接收超时** —— 读字节超时（`DHT22_ReadByte` 返回 0xFF） | `dht22.c:69` |
| `3` | **校验失败** | `dht22.c:80` |

> 调用方（`app_main.c:267` / `lora_app.c:297`）都只判 `== 0`，所以这个注释错误**没有造成功能问题**，只是会误导排查时对错误码的解读。

> 主循环 2 秒读一次给 OLED 用，LoRa 上报前 `lora_app.c` 又自己读一次 —— 两处各走各的，功能没问题，但读数可能差一个采样周期。**这是已知的技术债。**

### 4.6 ADC + DMA —— 光照与土壤（仅终端）

| 项 | 值 |
|----|----|
| ADC | **ADC1**（不是 ADC2） |
| 通道 | IN0 = PA0 光敏，IN1 = PA1 土壤，**同一个 ADC 的两路** |
| 转换模式 | **扫描 + 连续转换**，软件启动（无外部触发） |
| 通道数 | 2（Rank 1 = IN0，Rank 2 = IN1） |
| 采样时间 | 28.5 周期（两路相同） |
| 数据对齐 | 右对齐 |
| ADC 时钟 | PCLK2 ÷ 6 = 12MHz |
| DMA | **DMA1_Channel1**，外设→内存，半字，内存地址自增，**循环模式**，低优先级 |
| 目标缓冲 | `uint16_t adc1_values[2]`（`app_main.c`） |

**数据怎么流**：`HAL_ADC_Start_DMA(&hadc1, adc1_values, 2)` 启动一次，之后**硬件自动循环搬运**，CPU 完全不参与。主循环任何时候直接读 `adc1_values[0]`（光照）、`adc1_values[1]`（土壤）即可，永远是最新值。

**原始值 → 物理量**（两路算法相同）：

```
电压 V = adc_value × 3.3 / 4096          （12 位 ADC，参考电压 3.3V）
电阻 R = 10kΩ × V / (3.3 − V)            （与 10kΩ 分压电阻串联）
```

然后查表：

| 光敏 GL5528（14 个点） | 土壤 YX55769（4 档） |
|---|---|
| 阻值 → 照度 lux，100kΩ→0 lux … 1kΩ→350 lux | 阻值 → 等级 1~4，100kΩ→1 干燥 … 10kΩ→4 水分饱和 |

> **本工程没有使用 ADC2**。两路模拟量都挂在 ADC1 上，靠扫描模式 + DMA 一起搬。

### 4.7 PWM —— LED 与蜂鸣器（两块板都有）

| 定时器 | 时钟 | PSC | ARR | 频率 | 通道 | 引脚 |
|--------|------|-----|-----|------|------|------|
| TIM1 | 72MHz | 72−1 | 999 | **1 kHz** | CH1 | PA8（LED2） |
| TIM1 | 72MHz | 72−1 | 999 | **1 kHz** | **CH3N** | PB15（LED3） |
| TIM4 | 72MHz | 72−1 | 332 | **3003 Hz ≈ 3kHz** | CH4 | PB9（蜂鸣器） |

三路都是 PWM1 模式、高电平有效、自动重装载预装载使能。

**LED 的坑 —— 极性相反**：LED2/LED3 是**低电平导通**，所以 CCR 要取「周期 − 导通时间」，**CCR 越大灯越暗**。

| 档位 | 导通占空比 | CCR（周期 1000） |
|------|-----------|-----------------|
| 灭 | 0% | 1000 |
| 暗 | 15% | 850 |
| 中 | 50% | 500 |
| 亮 | 100% | 0 |

档位由照度决定（`pwm.c` 的 `LED_LightCtrl()`，判据是 `lux < 10` / `lux < 45`）：
**< 10 lux → 亮（100%）；10~44 lux → 中（50%）；≥ 45 lux → 暗（15%）**。

**PB15 是 TIM1_CH3N（互补通道）**：只使能了 CC3NE，按参考手册 OC3N 不会被反相，直接跟随 OC3REF，因此 PA8 和 PB15 共用同一个 CCR 值。**必须用 `HAL_TIMEx_PWMN_Start()` 启动**，调 `HAL_TIM_PWM_Start(..., TIM_CHANNEL_3)` 对 CH3N 无效。

**蜂鸣器是 3kHz 无源型**，高电平响，S8050 NPN 驱动。档位由 `BEEP_CO2Alarm()` 用**嵌套 if** 判出来，从宽到严：

```c
if      (co2 < 500  || co2 > 2000)  raw_level = 大声报警;   // 超出正常范围
else if (co2 < 800  || co2 > 1500)  raw_level = 小声预警;   // 接近阈值
else                                 raw_level = 不响;      // 正常
```

| 档位 | 占空比 | CO2 区间（ppm） | 备注 |
|------|-------|----------------|------|
| 不响 | 0% | **800 ~ 1500** | 正常区。**区间在中间，不是两端** |
| 小声预警 | 20% | 500~800 或 1500~2000 | 接近阈值 |
| 大声报警 | 50% | < 500 或 > 2000 | 超出正常范围 |

> **两头都报警**是有意的（温室场景：CO2 太低要补气、太高要通风）。
> 读传感器失败（`data_valid == 0`）时直接静音，避免拿上一次的残留值误报。
> **静音自锁**：按 SW1 → `BEEP_Ack()` 进 `SILENCED` 态，之后无论浓度多高都不响；
> 直到浓度**回到 `不响` 那一档**才自动解除，重新开始监控 —— 用 `raw_level`（未被静音覆盖的值）判断，不是「回到正常范围」，两者不等价。

无源蜂鸣器靠 PWM 方波驱动发声，**50% 占空比最响**（方波对称、谐波能量最大）；若给 100% 直流则根本不发声。

### 4.8 外部中断 EXTI（两块板都有）

| 引脚 | 触发沿 | 用途 | 中断服务内容 |
|------|-------|------|-------------|
| PB10 | **上升沿** | LoRa DIO1 收发中断 | 读一次芯片 IRQ 状态存进 `g_dio1_irq` 后返回 |
| PB13 | 下降沿 + 上拉 | SW1 报警复位键 | 延时 10ms 消抖 + 松手检测 → 只置 `g_reset_key_pressed = 1` |
| PB12 | 下降沿 + 上拉 | SW2（空闲未用） | 空 |

三者共用 `EXTI15_10_IRQn`，优先级 **0，0**（最高）。

**中断约定**：中断里**只置标志位，不做耗时操作、不调 `printf`**，真正的业务放到主循环。这是项目既定模式。

## 5. 数据是怎么流动的

### 5.1 终端：采集 → 无线发送

```
① 传感器
   PA0/PA1 ──ADC1 扫描──DMA1_Ch1 循环──→ adc1_values[2]（硬件自动，CPU 不参与）
   PC15    ──单总线软件时序──→ DHT22_ReadData() → 温度 / 湿度
   PA2/PA3 ──USART2 9600 空闲中断──→ co2_buffer[6] → CO2_get_data() → g_co2_value

② 主循环 app_main()（各任务独立计时，互不干扰）
   每 1000ms  : 读 CO2 → 更新 g_co2_value（同时决定蜂鸣器档位）
   每 2000ms  : 读 DHT22 → 喂 OLED
   每  500ms  : 读光照 → LED_LightCtrl() 调 LED 亮度
   每  500ms  : OLED_UI_Refresh() 把本机 4 项数据上屏
   随时       : BEEP_CO2Alarm() 按 CO2 阈值报警；SW1 中断置位则 BEEP_Ack() 静音

③ LoRa 状态机 LORA_AppService()（每轮 2500ms，全程非阻塞）
   ┌─ 开 500ms 接收窗口（等中控主动下发指令）
   ├─ 组 10 字节帧：从 adc1_values / DHT22 / g_co2_value 取值
   │    0xAA + 设备ID + 光照 + 土壤 + 温度 + 湿度 + CO2（小端）
   ├─ SPI1 写 FIFO → SetTx → 等 DIO1 的 TX_DONE 中断（空中 145ms）
   └─ 开 400ms 等 ACK（中控回的 3 字节 0xAA/ID/0x01，空中 104ms）
```

### 5.2 无线链路：终端 ↔ 中控

```
终端                                          中控
 │                                             │
 │  ── 上行 10 字节 @470.5MHz/SF9/BW125 ──→    │
 │     0xAA ID 光照 土壤 温度 湿度 CO2          │
 │                                             ├─ DIO1 上升沿中断 → g_dio1_irq
 │                                             ├─ 主循环 LORA_AppService() 解析
 │                                             │    校验长度(必须=10) → 校验帧头(0xAA)
 │                                             │    → 更新 g_lora_rx_frame → 串口打印
 │                                             ├─ SPI1 回 3 字节 ACK
 │  ←── ACK 3 字节（空中 104ms）──────────────  │
 │                                             │
 ├─ 收不到 ACK 下轮重试                        └─ 主循环：OLED 显示 g_lora_rx_frame
```

**时序账**（一轮最长）：500（RX 窗口）+ 145（上行）+ 400（ACK 窗口）= **1045ms < 2500ms** ✓

### 5.3 中控：接收 → 上屏 → 上云

```
① LoRa 收到包 → g_lora_rx_frame（全局结构体，含各字段 + RSSI/SNR + 帧计数）

② 主循环 app_main()（只有三块）
   LORA_AppService()              常驻接收 + 回 ACK
   MQTT_AppService()              连 WiFi+TCP+MQTT → 订阅五主题 → 每 5s 发布一次
                                  → 每 60s 心跳，失败自动整链重连（15s 后重试）
   OLED 刷新                      触发条件：收到新包（cnt 变化）或 2500ms 兜底

③ OLED 显示的是 g_lora_rx_frame（收到的数据），不是本机传感器
   温度/湿度 ── 无效时显示 --
   光照/土壤 ── 还没收到过包时显示 0
   CO2      ── 无效时显示 ---

④ MQTT 上云：把 g_lora_rx_frame 最新一包发到巴法云五个主题
   （Humidity / Temperature / light / soil / co2），负载为 "#值" 格式，失效项发 "#--"
```

> **中控板自己没有任何传感器**（PA0/PA1/PC15 未配置，ADC1 未启用），串口里只有 LoRa + WiFi 两类打印，**一条传感器日志都没有** —— 排查时别误判成卡住。

## 6. 中断与优先级

| 中断源 | 向量 | 优先级（抢占, 子） | 服务内容 |
|--------|------|------------------|---------|
| EXTI15_10 | `EXTI15_10_IRQn` | **0, 0** | LoRa DIO1 / SW1 / SW2 |
| USART1 | `USART1_IRQn` | **0, 0** | 调试口空闲接收 |
| USART2 | `USART2_IRQn` | **0, 0** | CO2（终端）/ ESP8266（中控） |
| DMA1_Channel1 | `DMA1_Channel1_IRQn` | **0, 0** | ADC 搬运完成（**仅终端**，中控没有 `Core/Src/dma.c`） |
| SysTick | `SysTick_IRQn` | **15, 0** | HAL 时基，1ms |

优先级分组：`NVIC_PRIORITYGROUP_4`（4 位全部给抢占优先级，16 级）。

> **三个外设中断都是抢占优先级 0，同级不互相抢占** —— 这保证了 LoRa 的中断不会被串口中断打断太久。
> 代价在后面 §4.8 提过：SW1 中断体里有 `delay_ms(10)` 和松手等待，按键按住不放会把 LoRa 的中断一起挡住。

## 附：容易踩错的几处

| 坑 | 说明 |
|----|------|
| **USART2 波特率两端不同** | 终端 9600（CO2）/ 中控 115200（ESP8266）。换模块前先确认对方默认波特率 |
| **PB15 是互补通道 CH3N** | 必须用 `HAL_TIMEx_PWMN_Start()`；PA8/PB15 共用同一个 CCR |
| **LED 低电平导通** | CCR 越大越暗，和直觉相反 |
| **DIO1 是上升沿触发** | 手册 §13.3.2.1（`DioxMask`）：IRQ 触发时 DIO 被**置位**（拉高），原文 "a **rising edge** of IRQ source TxDone … appears on DIO1"。代码注释里原先写的「下降沿」是错的 |
| **ADC 是双通道扫描 + DMA** | 只有 ADC1，没有 ADC2；两路模拟量一起搬 |
| **CO2 帧是大端** | `B2×256+B3`，和 LoRa 帧的小端相反 |
| **换 LoRa 帧格式要同步改两个工程** | 中控按长度判帧（必须 = 10 字节），一新一旧只会刷「长度异常的包」 |
